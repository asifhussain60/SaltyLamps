- Applying schema/seed to a database that doesn't have the tables yet:
  ```
  wrangler d1 execute salty-lamps-db --remote --file=d1/schema.sql
  wrangler d1 execute salty-lamps-db --remote --file=d1/seed.sql
  ```
- Applying schema to a database that **already has an older version of these tables** (e.g. you
  added a column since the table was created): `CREATE TABLE IF NOT EXISTS` is a no-op against an
  existing table. You need an explicit `ALTER TABLE ... ADD COLUMN ...` for each new column — this
  bit us once already; see the git history of `d1/schema.sql` around 2026-07-10 for the exact
  columns that needed this treatment (`slug`, `description`, `image`, `categories`, `tags`).

### Local D1 testing gotcha

`wrangler d1 execute --local` and `wrangler pages dev --d1 DB=<name>` can resolve to **different**
local SQLite files under `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/`, keyed by a hash that
doesn't obviously correspond to either command. If a local Function call reports `no such table`,
list the files there, find the one `wrangler pages dev` is actually bound to (check its startup
log line `env.DB (local-DB=...)`, or just try both), and load `schema.sql`/`seed.sql` into that
exact file directly with `sqlite3`, not via `wrangler d1 execute --local`.

## Functions (the backend)

All under `salty-lamps-site/functions/`, deployed automatically as part of the Pages build (no
separate Workers deploy):

- `api/products.js` — `GET /api/products`. Flattens `products` + `skus` into one flat product per
  SKU (a product with variants becomes one card per variant — the storefront has no in-page
  variant picker). Shared flattening logic lives in `lib/flatten-products.mjs` because
  `scripts/generate-seo.mjs` needs the exact same transform at build time.
- `api/checkout.js` — `POST /api/checkout`. Re-prices every cart line from D1 server-side (never
  trusts a client-sent price), creates a Stripe Checkout Session, returns its `url`.
- `api/webhook.js` — `POST /api/webhook`. Verifies the Stripe signature, records the order in
  `orders`/`order_items`, decrements stock for `quantity`-tracked SKUs only (binary
  in-stock/out-of-stock SKUs stay a manual toggle, matching how Wix treated them).
- `lib/flatten-products.mjs` — shared between the Worker runtime (`api/products.js`) and the Node
  build script (`scripts/generate-seo.mjs`, which queries D1's HTTP API directly at build time so
  sitemap/SEO generation doesn't depend on a deployment that hasn't happened yet).

## Pages secrets (production environment)

Set via `wrangler pages secret put <NAME> --project-name salty-lamps-proposal` (reads the value
from stdin — never pass it as a CLI argument, it'd land in shell history):

- `STRIPE_SECRET_KEY` — see [`stripe.md`](stripe.md)
- `STRIPE_WEBHOOK_SECRET` — see [`stripe.md`](stripe.md)
- `SITE_URL` — currently `https://salty-lamps-proposal.pages.dev`; used by `checkout.js` to build
  the Stripe success/cancel redirect URLs
- `RESEND_API_KEY` — transactional email sender; see `functions/lib/mailer.mjs`. **Set 2026-08-01.**
  Without it every send is recorded in the admin as `skipped` and nothing else changes. Full detail
  — account, current UAT sender, and what still blocks customer email — in [`email.md`](email.md).
  Cloudflare cannot send this mail itself; that question is settled in `email.md`, don't re-open it
- `MAIL_DRY_RUN` — dev/UAT only; renders and logs every email without handing it to the provider

(The former `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` pair is gone. The storefront form
submissions they served now post to `/api/support/enquiry`, which stores to D1 and emails the
owner.)

**Important:** Cloudflare Pages binds secrets to a deployment at *deploy time*. Setting a new
secret does not retroactively apply to the currently-live deployment — you must redeploy after
`wrangler pages secret put` for it to take effect. Learned this the hard way: the first live
checkout test after setting secrets failed with "You did not provide an API key" until a redeploy.

## Local development

`salty-lamps-site/.dev.vars` (gitignored) holds the same three custom secrets for
`wrangler pages dev` to pick up automatically. It is never committed. To recreate it from scratch:

```
STRIPE_SECRET_KEY=<get from Stripe dashboard — see stripe.md>
STRIPE_WEBHOOK_SECRET=<get from Stripe dashboard — see stripe.md>
SITE_URL=http://localhost:8788
```

Running locally with real D1 data:
```
wrangler pages dev dist --port 8799 --d1 DB=salty-lamps-db
```
(then load schema+seed into whichever local sqlite file it actually bound to — see the gotcha
above.)

### Admin portal local dev (live-reload UI + real backend)

The admin portal (`/admin`) calls `/api/admin/*`, which — like every other API route — only
exists inside Cloudflare Pages Functions. Plain `vite dev` doesn't run Functions at all, so
`/admin` pages fail to load anything under it. Two servers running together fix this:

```
# Terminal 1 — the real backend (D1 + R2 + Functions), no live reload needed
npm run build
wrangler pages dev dist --port 8788 --d1 DB=salty-lamps-db --r2 IMAGES=salty-lamps-images

# Terminal 2 — the fast-reloading UI; vite.config.js proxies /api/* to :8788
npm run dev
```

Load schema/seed/migrations into whichever local sqlite file `wrangler pages dev` bound to (see
the gotcha above) before testing admin CRUD. To point the proxy at a different backend port, set
`WRANGLER_PORT` before running `npm run dev`.

Admin auth in local dev: set `DEV_ADMIN_BYPASS=1` in `.dev.vars` so the middleware skips the
Cloudflare Access check (see `functions/api/admin/_middleware.js`). Never set this in production —
Pages secrets, not `.dev.vars`.
