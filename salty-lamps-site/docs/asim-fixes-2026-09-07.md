# Option previews and lighter photography — implementation and verification

Status: published to the production branch of the Cloudflare review application on 2026-09-07 at https://salty-lamps-proposal.pages.dev (deployment 466d44f8). Migrations 009 and 010 applied after a verified backup. This is not the customer domain, which remains on Wix pending owner-account cutover.

## Evaluation and chosen solution

The detail page changed the selected option, but the catalogue gave every option the same product cover. Quick view additionally read the group cover instead of the selected option. Gallery thumbnails were not interactive and generic collection scenes could appear as product photos. Saturation/brightness styling and a dark trade overlay made source colours heavier; mobile quick view cropped products.

The fix stores a photo assignment per SKU, validates that it belongs to that product, and resolves it through the shared catalogue transformation used by the API and build. Detail and quick view use the selected option. Galleries reset on option identity, support keyboard buttons, exclude other options' photos, and deduplicate paths. Missing/deleted assignments fall back to the product cover. Sold-out options remain previewable while purchase stays disabled. The owner can select or clear each option's photo in the product editor.

The public range contains 33 products and 73 options; 13 products have 53 selectable choices. Homepage/gallery counts now use products instead of counting each option as another product.

## Media scope and reproducibility

100 reviewed generated WebP assets cover the 73 option presentations and the remaining unique collection, lifestyle, brand and poster images. All 73 formerly active raster references have explicit replacements; semantically identical references reuse reviewed assets. Existing source files remain available. Videos themselves were not regenerated by this repair.

Product visuals are illustrative, not measured photographs of every physical size. The storefront says natural colour/shape vary and size is not shown to scale. Reference images guided generation, and pack counts, shapes and labels were reviewed. Two rejected generations were replaced before integration. New supplier photography can be assigned using the same owner controls without another frontend change.

`data/media-refresh.json` records source, prompt and SHA-256 checksums. `data/media-refresh-assignments.json` explicitly maps product UUID + SKU + option label to an asset. `npm run media:verify` verifies all source/output hashes and image formats; `npm run media:compile` generates the migration, frontend media mapping and fallback snapshot. Two consecutive compilations were byte-identical. Generative image creation itself is not deterministic; the approved outputs and their integration are fixed and checksum-verified.

Migration 009 adds the option-photo relationship. Migration 010 rejects missing, renamed or ambiguous catalogue options before mutation, uses stable commercial identities rather than numeric database IDs, and records completion. Reapplying it preserves subsequent owner changes. Price, stock and SKU records are unchanged. Existing uploaded image identities are retained; their paths are redirected to reviewed assets. Some retained gallery slots can consequently show the same image in the owner editor; public galleries deduplicate them.

## Release sequence

1. Back up current production catalogue/content tables, including `sku_images` when present. Retain the current deployed artifact and all original media. Check current product UUID/SKU/label triples against the assignment manifest; the migration fails if they have drifted.
2. Apply `009-option-images.sql` before deploying the new API, since its queries require that table. This is additive and compatible with the old storefront.
3. Publish the verified application and its 100 static image files. Use the reviewed committed content snapshot for this release (`CONTENT_SNAPSHOT_SOURCE=committed npm run build`).
4. Apply `010-lighter-catalogue.sql` using the transactional D1 file executor. Existing earlier collection migrations remain prerequisites. Do not split statements into independently committed fragments.
5. Confirm live option images, owner assignment persistence, galleries, mobile quick view and cart identity. Refresh the committed snapshot from production after deployment.

Rollback should restore only the affected catalogue/content rows from the pre-release backup and return to the previous artifact, preserving newer orders and inventory transactions. Do not restore a whole production database over intervening orders. The additive option-image table may remain for compatibility. Keep the release ledger consistent with any targeted reversal before attempting to reapply the refresh.
